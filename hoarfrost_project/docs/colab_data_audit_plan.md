# План аудита и нормализации исходных данных для Colab

Цель этого этапа — выделить воспроизводимый предварительный блок обработки данных, который запускается **до** `calibration.py`, `makkonen_model.py` и последующего coupling pipeline. Такой порядок соответствует QA/QC-подходу для метеорологических временных рядов: сначала приводится время, структура и пропуски, затем строится ряд целевой частоты и только после этого выполняются физические расчёты.[cite:300][cite:303]

## Входные файлы

Аудит и нормализация выполняются на уровне исходных файлов:

- `Sensor-VL-module-3-No0039-wide-ffill.csv` — основной сенсорный ряд, содержащий поле времени `created_at` и сенсорные переменные вроде `tcab`, `tvozd`, `rh`, `iideistv`, `ugol1`, `ugol2`.[cite:127]
- `Meteostation-2304-MSR0011-wide-ffill.csv` — ряд метеостанции, который уже используется как источник давления и ветра в текущем калибровочном пайплайне.[cite:121]
- `METAR-Yakutsk.csv` или эквивалентный METAR-файл Якутска — внешний ряд облачности и аэродромных наблюдений; по структуре он отличается от двух первых файлов и требует отдельного парсинга.[cite:118]

## Архитектурное решение

Предобработка оформляется в двух формах одновременно:

1. **Отдельный Colab-блок / notebook-этап** — для ручного аудита, визуального контроля и воспроизводимой диагностики качества данных.
2. **Встроенный модуль модели** (`src/data_normalization.py` в следующей итерации) — для автоматического запуска в основном pipeline перед `calibration.py`.

Такое разделение нужно, чтобы не смешивать QA/QC исходных наблюдений с физической моделью изморози и не маскировать ошибки данных под «поведение модели».[cite:300][cite:303]

## Что именно анализируется

### 1. Временная структура

Для каждого файла нужно проверить:

- наличие и корректный парсинг временной колонки;
- сортировку по времени;
- дубликаты timestamp;
- отрицательные шаги времени или нарушения порядка;
- распределение `delta_t` между соседними наблюдениями;
- типичный шаг дискретизации и его устойчивость по месяцам/сезонам.[cite:303][cite:300]

Это обязательный этап, потому что для метеорологических временных рядов типовые проблемы начинаются именно с несогласованного времени, дубликатов и нерегулярных интервалов.[cite:303]

### 2. Пропуски и разрывы

Для каждого ряда нужно выделить gap-сегменты и классифицировать их по длительности:

- короткие gaps;
- средние gaps;
- длинные gaps;
- очень длинные gaps / структурные разрывы.

Практика gap-filling для климатических и снегомерных рядов допускает линейное заполнение лишь для коротких пропусков, а длинные интервалы требуют либо внешних источников, либо исключения из непрерывного анализа.[cite:298][cite:294]

### 3. Семантика переменных

Нельзя нормализовать все поля одинаково. Политика должна зависеть от физического смысла признака:

- **плавные метеопеременные** (`ta`, `rh`, `pressure`, иногда `wind`) допускают ограниченную локальную интерполяцию только на коротких gaps;[cite:294][cite:298]
- **дискретные/категориальные признаки** (например, код облачности из METAR) не должны интерполироваться как непрерывные числа без явного правила преобразования;[cite:299][cite:308]
- **токовые и событийные сигналы**, а также derived/model state-поля, нельзя «дорисовывать» так же свободно, как температуру;
- **состояния модели** (`H`, `rho_t`, `mass_per_m`, `prev_delta_T_c`) вообще не относятся к исходным наблюдениям и не подлежат заполнению как сырые данные.

## Политика по облачности METAR

METAR кодирует облачность в октах/категориях: FEW соответствует 1–2 октавам, SCT — 3–4, BKN — 5–7, OVC — 8.[cite:299][cite:302][cite:308]

Для интеграции METAR в модель предлагается такой порядок:

1. распарсить временную метку METAR;
2. выделить облачные группы и перевести их в количественный показатель облачности `n_tenths` или эквивалентную шкалу покрытия;
3. при наличии нескольких слоёв выбрать правило агрегации — обычно максимум покрытия по небу как proxy для общей облачности;
4. не выполнять обычную линейную интерполяцию кодов FEW/SCT/BKN/OVC между дальними наблюдениями, а сначала переводить их в физически интерпретируемую шкалу покрытия.[cite:299][cite:308]

## Что не делается

На этом этапе не выполняются:

- подгонка физической модели под данные;
- искусственное сглаживание длинных разрывов внутренней интерполяцией;
- интерполяция модельных состояний;
- замена внешних источников псевдозаполнением там, где gap должен разрывать эпизод моделирования.[cite:298][cite:300]

Отдельно фиксируется решение: **подгонка не используется**. Модель должна работать на нормализованных, но не «подогнанных» данных наблюдений.[cite:300]

## Практический следующий шаг в Colab

Следующий Colab-этап должен сделать для всех трёх файлов однотипный аудит:

- прочитать файл и корректно распознать timestamps;
- вычислить `delta_t`;
- найти дубликаты и нарушения порядка;
- оценить типичный шаг дискретизации;
- выделить все gap-сегменты и их длительность;
- построить покрытие по месяцам;
- подготовить policy table: какие поля допускают локальную интерполяцию, какие — только forward/backward fill в очень узких пределах, а какие должны разрывать эпизод.

Именно после этого этапа можно переходить к реализации `src/data_normalization.py` и затем подключать результат к `calibration.py` и физической части модели.[cite:300][cite:303][cite:298]
